# Security and deployment boundaries

Security reports should be shared privately with the repository owner. Include the affected
revision, minimal local reproduction, expected authorization boundary and observed outcome.
Use dummy accounts and avoid real payments, real customer data or other operators' servers.

## Application controls

Staff access requires permission checks, recent password confirmation and confirmed TOTP by
default. Customer orders, carts and support tickets are scoped to their owner. Internal ticket
notes are excluded from customer queries. Content is rendered from Markdown with raw HTML
escaped and unsafe link schemes blocked. Uploaded raster images are bounded and re-encoded;
SVG, HTML and executable uploads are not accepted.

Money uses integer minor units. Signed payment events enter a durable deduplicated inbox.
Order and wallet transitions use database transactions and row locks. Real provider sandbox
validation and concurrent InnoDB tests remain necessary before a release is accepted.
An HTTP return from a checkout does not authorize a payment or delivery.

## Cloudflare profile

Use end-to-end HTTPS with [Full (strict)](https://developers.cloudflare.com/ssl/origin-configuration/ssl-modes/full-strict/).
Enable `VIBECRAFT_PROXY_MODE=cloudflare` only when Cloudflare is the actual reverse proxy.
CF-Connecting-IP is accepted only when the TCP peer is in the trusted edge address list.
Spoofed forwarding headers from direct clients must not affect identity or throttling.
Restrict direct origin access at the host firewall where hosting permits it.

Do not cache login, registration, reset/verification, account, admin, cart, checkout, orders,
tickets or API routes. Bypass managed browser challenges for authenticated provider webhooks
and bridge routes as required for delivery, while retaining application signatures and limits.
Never create a blanket WAF bypass for the whole domain.

Turnstile requires [server-side Siteverify validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/),
matching hostname and action, and rejection of expired or reused tokens. Configure allowed
widget hostnames and separate production/test keys. A widget alone offers no authorization.

HSTS is opt-in after HTTPS and all affected subdomains have been verified. Strict CSP and
nonce-bearing styles/scripts are generated by the application. CAPTCHA and payment origins
are permitted only when their integrations are configured. Keep security patches current.

No live Cloudflare account, zone, WAF policy, origin firewall or real provider account is
certified by repository tests. Record those checks separately using the final deployed profile.

## Secrets and backup

Keep `.env`, APP_KEY, database credentials, SMTP credentials, webhook secrets, TOTP recovery
codes and bridge keys out of version control. Logs and exports must redact secrets. Use encrypted
backups outside the public web root and verify restoration regularly. Production APP_DEBUG
must be false. Point the document root to public; the package-root layout is only for Apache with mod_rewrite,
where the bundled .htaccess routes every request into public and refuses everything else.

## Scheduled status queries

Java and Bedrock probes share a monotonic budget across connect, writes and every partial
read. Progress cannot reset that budget. Scheduled refreshes take a bounded, oldest-due batch
and stop starting new probes when the batch budget expires, preserving time for other cron work.
PHP's OS DNS resolver remains blocking: elapsed resolution is charged to the budget, but its
own blocking limit depends on the host resolver configuration. Verify that bound on the target
hosting profile; it is not a hard process deadline or a substitute for cron/runtime limits.

## Delivery guarantee

A web queue and a game command cannot share a database transaction. Delivery is retried with
a stable ID; the game side needs a durable journal and careful recovery. Arbitrary game commands
cannot promise mathematically exact-once execution across a server crash. Ambiguous execution
requires manual review or an idempotent game-side operation. Never erase that distinction in
operator messaging or billing promises.
